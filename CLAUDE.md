### Running the integration test suite

If the dev machine's default Python is newer than 3.13 (e.g. 3.14), it can't install `homeassistant==2025.10.1` directly — a transitive dependency (`pydantic-core`) has no prebuilt wheel for it and fails to build from source. Use a **Python 3.13** virtualenv instead — this is verified working, not theoretical (the whole suite passes this way):

```bash
uv venv --python 3.13 .venv-test
uv pip install --python .venv-test/bin/python -r requirements_test.txt
.venv-test/bin/python -m pytest -q
```

(`requirements_test.txt` pins `pycares<5` — see the comment above that line in the file for why: `aiodns==3.5.0`, pinned by `homeassistant==2025.10.1`, breaks on newer pycares. Test-env-only, doesn't affect the shipped integration.)

This runs entirely locally, on the exact pinned stack — don't wait for CI to find out whether it works.

### Running hassfest locally

CI's `validate.yml` runs `hassfest` (via `home-assistant/actions/hassfest@master`) and HACS validation. `hassfest` isn't a pip package, but it *can* be run locally — verified working end-to-end (`Integrations: 1, Invalid integrations: 0`), not just theoretical — by sparse-checking-out the relevant scripts from `home-assistant/core` at the tag matching this project's pinned HA version (`2025.10.1`):

```bash
# separate scratch venv with ruff (hassfest shells out to it) — capture the absolute
# path *before* cd'ing elsewhere below, or every reference to it after that breaks
uv venv --python 3.13 .venv-hassfest
VENV="$PWD/.venv-hassfest"
uv pip install --python "$VENV/bin/python" -r requirements_test.txt ruff

# sparse-checkout just the scripts hassfest needs, at the pinned tag
git init /tmp/core-hassfest && cd /tmp/core-hassfest
git remote add origin https://github.com/home-assistant/core.git
git sparse-checkout init --cone
git sparse-checkout set script pyproject.toml
git fetch --depth 1 origin 2025.10.1
git checkout FETCH_HEAD

rm -rf homeassistant  # only present with some checkout methods; shadows the pip-installed package if it is

# hassfest's docker.py imports turbojpeg transitively (via go2rtc -> camera -> img_util)
# even though it's irrelevant to this integration — stub it rather than installing the
# native lib:
cat > "$("$VENV/bin/python" -c 'import site; print(site.getsitepackages()[0])')/turbojpeg.py" << 'EOF'
class TurboJPEG:
    def __init__(self, *a, **k): raise NotImplementedError("stub — not for runtime use")
EOF

PATH="$VENV/bin:$PATH" "$VENV/bin/python" -m script.hassfest \
    --action validate --integration-path <this-repo>/custom_components/carr_ab64
```

Do this before pushing, not after — it catches manifest/translation/config-flow issues (e.g. `manifest.json` keys not being in hassfest's required sort order) that CI would otherwise be the first to surface.

## Running the test script

```bash
pip install pymodbus
python references/ac-modbus-ab64-test.py --host 192.168.14.149 --port 502 --unit-id 2
```

- `--once` sends a single read and exits instead of polling in a loop.
- `--interval` / `--timeout` control poll cadence and per-request timeout.
- This script has no Home Assistant dependency — it's meant to confirm the AC is reachable over the network (from WSL2 or elsewhere) before wiring up the real integration.
- If the connection hangs in WSL2 but works from Windows, WSL2 networking mode is the likely cause: "mirrored" mode is required to reliably reach LAN devices; NAT mode can be flaky.

## Architecture: the 4-layer chain

```
AC indoor unit (control board)
      │  AB Bus (proprietary)
      ▼
AB64 box (Toshiba ↔ Modbus translator)
      │  RS-485, Modbus RTU
      ▼
TCP↔RTU gateway (e.g. Elfin EW11)
      │  Ethernet, Modbus TCP
      ▼
HA integration (Modbus TCP client)
```

Each link can fail independently and silently. The AB64 is a protocol translator, not a Modbus-native device — one side speaks the AC's proprietary AB Bus, the other speaks Modbus RTU. It is powered from the AB Bus side (from the AC), not from the Modbus side. Unit-id address space is 1–64 (corrected 2026-08-05 — see the DIP-switch bullet below; it used to be documented as 0–63, which was off by one).

Confirmed-working configuration from this bring-up: IP `192.168.14.149:502`, unit-id `2`, `9600 8N2`.

## Non-obvious facts that must carry into any integration built from this reference

**Historical context, still load-bearing**: these facts come from the 2026-07-31 bring-up session referenced above. They are no longer forward-looking guidance for "a future integration" — they are the reasons behind specific decisions already implemented in `custom_components/carr_ab64/` (e.g. shared hub/refcount in `hub.py`, the 65535 debounce in `coordinator.py`, FC03-only in `hub.py`). Treat them as design-rationale documentation for the existing code, not just a checklist for someone starting fresh.

These are documented in full (with the reasoning/evidence behind each) in `references/ac-modbus-ab64-reference.md` — read it before implementing anything that touches this device. Highlights:

- **Only FC03 (Holding Registers) works.** FC04 (Input Registers) is not supported, even for read-only fields. Don't offer it as an option. This is empirical-only — the vendor's user manual (Intesis INMBSTOS001R000 r2.7 EN) never mentions Modbus function codes at all, so this fact rests on the bring-up log, not on documentation.
- **Multiple AB64 boxes sharing one gateway is the vendor's standard topology, not an edge case.** The manual's own wiring diagram shows one AB64 wired 1:1 to exactly one AC indoor unit; multiple such 1:1 pairs can share one RS-485 bus/gateway, distinguished by unit-id (confirmed **1–64**, 64 slots, from the full SW1+SW2 DIP table — see the corrected DIP-switch bullet below). **Decision 2026-08-05: don't state a maximum box-count figure anywhere in this repo, at all.** This reverses the M-3 fix (`unitstep-review.md`) from earlier the same day, which kept a hedged "up to 64 boxes" figure with a long qualifier explaining it was an inference from the address space, not a vendor-stated device maximum. On reflection the qualifier didn't fix the underlying problem — there's no vendor-stated device-count maximum and no independently-verified RS-485 electrical limit to cite, so *any* number here, however carefully hedged, invites being read as a ceiling. The evidence-backed number worth giving users instead is the poll-bandwidth constraint documented in `README.md`'s poll-interval option (the bus saturates around 4 units at a 1s poll interval) — that's what should guide how many boxes someone puts on one bus, not an address-space count. If a future change is tempted to reintroduce a "max boxes" figure (even hedged), don't — point to the bus-math number instead. Any integration MUST share the underlying Modbus connection/lock across config entries that target the same host:port — a per-config-entry connection breaks the moment a user has two AC units on one gateway.
- **Register 11 == 65535 can be transiently true for up to ~17 seconds after power-up or an AC-side blip** (5s LED warm-up + a documented 12-second internal AB64→AC comms timeout) **and this is not a permanent fault.** Debounce before surfacing it as a persistent problem/binary_sensor state, or every HA restart will look like a hardware failure.
- **DIP switch → unit-id is a 1-based formula, not a direct reading.** `unit-id = SW2 × 16 + SW1 + 1`. Verified against the vendor's full SW1/SW2 table (sent by the user 2026-08-05): (0,0)→1, (0,1)→2, (1,0)→17, (3,B)→60 — the table is 1-based, so the true address space is **1–64**, not 0–63. **Corrected 2026-08-05**: this bullet used to say "don't trust the DIP-switch address" because the unit-id that worked in the 2026-07-31 bring-up (`2`) didn't match what the switches appeared to show (`1`) — that framing was wrong. The switches were read correctly (confirmed twice); the team simply forgot the `+1`: switches (SW2=0, SW1=1) → `0×16 + 1 + 1 = 2`, exactly the working unit-id. The lesson is "always run the DIP reading through the formula," not "don't trust the switches." Scanning a unit-id range and confirming against a real register read is still worth keeping in the config flow — as a safety net for anyone who fat-fingers the formula (as this team did), not because the hardware/DIP reading is unreliable.
- **DIP switches only take effect on power-up.** Changing SW1/SW2 (address) or SW3 (baudrate) requires a full power cycle of the AB64 box, not just re-polling.
- **The AB64's two terminal blocks are easy to cross.** `A B — AC UNIT` goes to the AC control board (AB Bus, not Modbus); `MODBUS RS-485 — B A G` goes to the TCP↔RTU gateway. Note the gateway-side terminal is silkscreened `B A G` left-to-right, not the more intuitive `A B G` — compare printed letters, not position. Wrong wiring here produces total silence at every layer (TCP connects fine, gateway forwards fine) with no distinguishing symptom.
- **Register 11 == 65535 is a distinct fault class.** It means the AB64 itself has lost its AB Bus link to the AC (hardware-level), separate from both normal AC error codes and a Modbus timeout. Surface it as "gateway can't reach the unit," not as a generic AC error.
- **Separate "TCP connect failed" from "TCP connected but Modbus timed out."** These point to different layers (network/gateway config vs. addressing/wiring) — collapsing both into a generic "unavailable" state defeats debugging.
- **Serialize all register access through one coordinator/connection.** This is RS-485 behind a single TCP↔RTU gateway; concurrent requests from multiple entities will collide or serialize unpredictably. Don't create one Modbus client per entity.
- **Port defaults vary per gateway — the EW11 used in this bring-up actually defaulted to 8899, not 502.** That fact is still true and is why the config flow's port field warns about it directly. **However, as of 2026-08-04 the user decided the config flow *should* default the port field to `502`** (the Modbus TCP standard, and the same default `homeassistant/components/modbus` itself uses) — this reverses the original guidance here, which said not to default it to 502 at all. Reasoning: leaving the field with no default rendered as `0` on the frontend, which is wrong 100% of the time, strictly worse than a default that's sometimes wrong. The EW11/8899 risk is mitigated by keeping the 8899 warning in the port field's `data_description` (guarded by a test that fails if it's ever removed) rather than by refusing to default the field. IP, port, and unit-id remain three separate required fields — that part of the original guidance still holds.
- **The gateway's TX/RX byte counters (Status page) are the fastest diagnostic tool** for bisecting where a request dies: network-side received bytes, serial-side sent bytes, serial-side received bytes — check in that order.
- **AB64 has two independent status LEDs**: blue = Modbus frame received with correct address; green = AB Bus link to the AC unit. They indicate different link segments — don't conflate them when troubleshooting.
- **Decision 2026-08-05 — config flow UX + polling, from real-world v0.1.2 usage feedback:**
  - **No auto-pick of unit-id, ever** — even when a scan finds exactly one responding unit-id, the config flow still shows a confirmation step rather than silently using it. The previous behavior (silent auto-pick on a single match) meant three different flows depending on scan results, which users could not predict.
  - unit-id lives in the *first* step alongside name/host/port, not a separate step — leaving it blank still triggers a scan.
  - The scan itself is kept (it's not being removed) — see the corrected DIP-switch bullet above for why: it's a safety net for formula mistakes, not because DIP hardware is unreliable.
  - `MIN_SCAN_INTERVAL` lowered from 10s to 1s (default poll interval was still 30s at the time of this decision — see the 2026-08-05 poll-interval bus-math decision below, which later lowered the *default* itself to 5s; this bullet only ever changed the floor a user can configure, and `MIN_SCAN_INTERVAL` itself is still 1s unchanged). This came from a user reporting climate-card updates taking ~10s after issuing a command; polling faster is the fix, paired with tolerating a few consecutive failed reads (see next bullet) so a faster poll doesn't make transient RS-485 hiccups visibly flicker every entity.
  - **Do not add optimistic state** (showing the just-issued command's value immediately instead of what was actually read back), under any circumstance, even if it looks like an obvious UX improvement. Reasoning, stated directly by the user: people buy this integration specifically because they want a value that reflects what the hardware actually reports — showing the commanded value instead of the read-back value defeats the reason they installed it. If a future change proposes optimistic state to "fix" perceived latency, that is re-introducing something the user explicitly rejected — poll faster / tolerate more misses instead.
  - **Decision 2026-08-05 (0.1.7) — post-write refresh: schedule one extra read ~2s after every write, in addition to the existing immediate one.** Motivated by a real latency measurement the same day (see `references/ac-modbus-ab64-reference.md` section 10): three back-to-back writes measured 1.65–1.76s round-trip via HA MCP, of which ~0.36s was tool overhead, putting actual AB64/AC write-to-readback latency at **~1.3–1.4s**. The existing immediate post-write read (`async_write()` → `async_refresh()`) fires *before* that ~1s hardware settling time, so it reliably reads back the stale value — the new value only ever showed up on the next scheduled poll, which at the 30s default made every command feel far slower than the hardware actually is. The ~2s extra read closes that gap for anyone not already polling that fast. **This does not conflict with the "no optimistic state" rule above** — the extra read is a genuine register read at the ~2s mark, not a display of the commanded value; if the AC hadn't actually applied the change yet, the card would show that unchanged value, same as it always has. If `scan_interval` is already ≤ 2s, skip scheduling the extra read — normal polling already covers that cadence, so it would just be a duplicate, wasted read.
- **Decision 2026-08-05 — advanced telemetry, from the first real-hardware ramp test of this project (Carrier 38TGV0391A3 / 40TGV0391UP, 3-phase):**
  - Deliberately confirmed by ramp test (lowering setpoint 22→18 and sampling every 20s while load ramped up — see the results table in `references/ac-modbus-ab64-reference.md`): the advanced register blocks exist and respond on this unit; the raw-to-°C temperature scale is 1:1 (every temperature field moved the correct direction as load changed); TA (register 4012) tracks the real room temperature, not the setpoint (observed setpoint held at 18°C while TA read 21°C and drifted down toward 20°C).
  - **Compressor current (register 4415) has no confirmed unit and must not be divided by 10 or scaled in any way** — raw int, no `device_class`, no unit string. The old assumption (raw ÷ 10 = amps) is disproven: at the observed raw range (29–65) that would mean 2.9–6.5A on a 3-phase compressor, which doesn't square with a discharge temp climbing into the 80s°C under load. Do not reintroduce a division — with data from only one unit, any scaling factor is an unfalsifiable guess. Reasoning to reject "amps directly" instead of a /10 guess: 29–65A on 3-phase implies ~17–38kW input power for an ~11kW-cooling-capacity unit, which is physically implausible.
  - **Compressor speed (register 4417) is `rps` (revolutions per second), not rpm, and is not multiplied.** Ruled out by physics, not by manual confirmation: the observed range (23–58) is far too low for rpm on a running compressor under a rising discharge temperature, but is a plausible rps range. `REVOLUTIONS_PER_SECOND` isn't a constant Home Assistant provides — define it locally.
  - **The two outdoor-fan RPM fields stay `rpm`** — same physics argument in reverse: at the observed magnitudes, reading them as rps would imply an impossible fan speed (566 rps ≈ 34,000 rpm).
  - **`current_temperature` (register 4012, TA) is now read and exposed by default, without opening the advanced telemetry option** — the climate card shows room temperature from installation onward. Reasoning: comparable integrations expose this without an opt-in, and it's core to why someone installs a direct-Modbus AC integration in the first place.
  - **Decision 2026-08-05 (0.1.7) — the `indoor_temp` advanced field (register 4012, TA) is now also created unconditionally as its own sensor entity, alongside `climate.current_temperature`.** This is an **extension of the TA-default policy above, not a reversal of it** — the "default = only registers confirmed present on every model" bar hasn't moved; TA is still the only advanced field considered safe to default on, for the same reason as before (every AC needs a return-air thermistor for its own control loop). What changed is that TA's value is now exposed through **two** entities instead of one: the existing `climate.current_temperature` attribute, and a standalone sensor entity (field key `indoor_temp` internally, but note the resulting **`entity_id` is `sensor.<name>_indoor_temperature_ta`, not `sensor.<name>_indoor_temp`** — HA derives it from the entity's translated display name, "Indoor temperature (TA)", not from the field key; see `README.md`'s Entities table, which had this wrong until 2026-08-05 review `roomtemp-review.md` m-2). Since the indoor block is already read every poll regardless (to feed the climate attribute), creating the extra entity for the same already-read value costs **zero additional bus time** — it's a UI/UX addition (the value is graphable/usable in long-term statistics as a sensor, which a climate attribute isn't), not a new register or a new read. The other 11 advanced fields are unaffected — still opt-in behind "Enable advanced telemetry sensors," for the same unverified-across-models reason as before.
  - **The general policy going forward: only add a field to the *default* read/entity set once it's confirmed present across the register blocks this integration already treats as universal** (the basic block, and now TA) — everything else stays opt-in behind "Enable advanced telemetry sensors," because this project has so far only verified these registers against **one** real unit (see the "tested against a single real unit" note in `README.md`'s Known limitations). This is a deliberately narrow bar: the project doesn't yet have evidence about which advanced registers are present across the wider range of hardware the AB64's manual says it covers, so defaulting more than TA on would risk exposing fields as real values that are actually just absent-register noise on hardware nobody's tested yet.
  - **Reading the indoor advanced block now requires a block-level backoff, and this is mandatory, not optional, specifically because of the previous bullet.** Before this change, advanced telemetry was opt-in, so a user who turned it on implicitly accepted the risk of an unsupported register block. Now that the indoor block (which includes TA) is read unconditionally for every installation, that risk lands on every user by default, not just people who opted in — a block that doesn't exist on someone's hardware and simply never responds (a timeout, not a clean Modbus exception) would otherwise cost a full read-timeout on every single poll, forever, which is especially bad at the new 1s poll floor. Backoff after a threshold of consecutive failures, with periodic retry, turns a permanent per-poll tax into an occasional one. Separately — and this cannot be caught by the same mechanism — **a register that doesn't exist can come back as a plain `0` instead of an exception or `0xFFFF`, which is indistinguishable from a real reading**; this is a data-quality caveat that has to be documented for users (see `README.md`), not something backoff or any other code path can detect automatically.
  - **Corrected same day (2026-08-05): the backoff cooldown is a ladder (`UNSUPPORTED_BLOCK_RETRY_LADDER = (60, 300, 600)` seconds), not the flat 600s cooldown this decision originally shipped with.** The original flat 600s cooldown paired a trip threshold (3 consecutive failures) that's count-based with a penalty that's time-based, and at the new 1s poll floor those two don't scale together: a block can trip in as little as ~3–18 seconds — much less confirmation than the 30s-default case this was designed around — yet still eat the full 10-minute penalty. The much more common case in practice is a brief transient hiccup that would have cleared itself within tens of seconds, not a genuinely missing register. The ladder (1 min → 5 min → 10 min, resetting to the first rung immediately on any successful read) lets that common transient case recover within a minute instead of ten, while a block that's *actually* unsupported still climbs the same ladder and lands at the same 10-minute steady state as before — so the "register genuinely doesn't exist" case is no worse off than the original flat-600s design.
- **Decision 2026-08-05 (0.1.8) — default poll interval lowered `DEFAULT_SCAN_INTERVAL` 30 → 5 seconds, based on measured bus math, not a guess.** A single register-block read is **~115ms measured** (real DEBUG-log timing on the reference hardware, 2026-08-05 — this is a measurement from one unit, not a vendor spec). At 2 blocks/poll (the default: basic + indoor) that's **230ms/unit/poll round**; with advanced telemetry enabled (3 blocks: + outdoor) it's **345ms/unit/poll round**. The user's realistic-max assumption for this integration is **4 AB64 boxes sharing one gateway/bus** (this is an assumption about expected usage, not a hard limit — see the "don't state a maximum box-count figure anywhere in this repo" rule in the multiple-AB64-boxes bullet above, still in force) — at that count, a 5s interval uses **18.4%** of the bus (default reads) or **27.6%** (advanced enabled), both comfortably inside the "recommended ≤50%" zone. Full bus-time and recommended-interval tables (by unit count, at 1s/5s/30s) live in `README.md`'s **Poll interval** section — don't duplicate them here, that's the one place they're maintained.
  - **No migration.** Config entries with an explicit `scan_interval` already set in options keep that value exactly as-is. Entries with empty options (never touched the Configure page) silently pick up the new default (30 → 5, a 6x traffic increase) on upgrade. This was a deliberate call, not an oversight: that group never chose 30 themselves, it was just the shipped default, and changing a default is the normal way defaults change. The risk this creates — someone with several AB64 boxes on one shared bus suddenly polling 6x faster — is called out explicitly in the 0.1.8 release notes rather than mitigated in code.
  - **Permanent constraint, not just true today: `DEFAULT_SCAN_INTERVAL` must always be `> POST_WRITE_REFRESH_DELAY` (currently 2s).** At or below that, the post-write refresh scheduling in the coordinator (see the 0.1.7 decision above) silently stops ever firing — normal polling would already cover that cadence, so the code skips scheduling the extra read, and nobody would notice until someone asked why writes felt slow again. There is a test asserting this relationship directly (not just the two literal values) — if a future change wants to lower the default further, that test is the thing to read first, and lowering `POST_WRITE_REFRESH_DELAY` to compensate is not a free move either, since that delay is itself sized to the ~1.3–1.4s measured hardware write-to-readback latency (see the 0.1.7 decision above).
  - `MIN_SCAN_INTERVAL` is unchanged at 1 — this decision only moved the *default*, not the floor a user can configure down to.
- **Decision 2026-08-07 — reverses the en-only translation policy: `translations/th.json` added.** `th.json` was introduced in commit `2ed4ec6`, which shipped in tag `0.1.8` (no `v` prefix — the tag points at `9b50b7a`, two commits later; `v0.1.8` is only the display name of the GitHub release, "Latest", not the tag itself). The project previously stated "English only, no `th.json`" (see the old "Known limitations" wording in `README.md`, now updated). The user reversed that call on 2026-08-07 — it's their call to make, and the team follows it. `.claude/agents/planner.md`, `reviewer.md`, and `docs-engineer.md` were updated by the planner the same day to reflect this; `qa-engineer.md` was also updated, with its own §4b covering the new key-parity/number tests (see `.claude/shared/plan-thai.md`).
  - **Scope: all three blocks of `strings.json` are translated — `config` (25) + `options` (6) + `entity` (13 sensor names + 1 binary_sensor name) = 45 keys total.** `th.json` is a complete translation, not a partial one.
  - **Corrected 2026-08-07 (same day, after round 1 shipped with `config`+`options` only): the original reasoning for excluding `entity` was factually wrong, verified against source, not just re-argued.** Round 1 of this decision said translating `entity` would make a Thai-language HA instance generate a different `entity_id` than the one in `README.md`'s Entities table. **That doesn't happen, and can't** — confirmed by reading the actual installed `homeassistant==2025.10.1` source in `.venv-test`: `Entity.suggested_object_id` (which becomes `entity_id`) is built from `platform_data.object_id_platform_translations` (`helpers/entity.py`), which in turn is loaded using `object_id_language` (`helpers/entity_platform.py`, `async_load_translations`) — not `hass.config.language` directly:
    ```python
    object_id_language = (
        hass.config.language if hass.config.language in languages.NATIVE_ENTITY_IDS
        else languages.DEFAULT_LANGUAGE  # "en"
    )
    ```
    `NATIVE_ENTITY_IDS` (`homeassistant/generated/languages.py`) is a fixed list of Latin-script languages (`af`, `bs`, `ca`, `cs`, ... `sv`, `tr`) and **does not include `th`** — confirmed by direct inspection, not assumption. So for any Thai-language HA instance, `object_id_language` falls back to `"en"` regardless of what `th.json` contains, and `entity_id` generation always reads the English `entity` translations. Meanwhile the entity's **display name** (the `name` property, `helpers/entity.py`) uses `platform_translations`, loaded from `hass.config.language` directly (i.e. actually `"th"`) — so the display name *does* follow the translated string. Net effect: translating `entity` makes the **name shown on the card** Thai, while `entity_id` **stays English**, automatically, as a Home Assistant platform behavior for any non-Latin-script language (this includes Japanese, Chinese, Korean, Russian — not something specific to Thai or to this integration). This is the opposite of round 1's conclusion, and the correct one — round 1's reasoning is left here struck through in spirit (not literally deleted) so a future reader understands *why* the scope changed, per this file's own historical-context convention.
  - **Residual risk, to document rather than fix — `NATIVE_ENTITY_IDS` is a list Home Assistant itself generates and could change in a future HA release.** If a future HA version adds `th` to `NATIVE_ENTITY_IDS`, `object_id_language` would then resolve to `"th"` for Thai instances, and `entity_id` generation would switch to reading the Thai `entity` translations instead of falling back to English — meaning **entities created for the first time after that HA upgrade**, on a Thai-language instance, would get `entity_id`s slugified from Thai text, no longer matching `README.md`'s Entities table. **Entities that already exist are not affected** — `entity_id` is fixed at creation time and never recalculated from translations afterward. There is a QA test guarding the current behavior (see `qa-engineer.md`, AC-6 in `plan-thai.md`) that will need attention if this ever changes upstream. **This risk is not written into `README.md`** — an end user has no action to take about it either way, so it belongs here as engineering context, not user-facing documentation.
  - **Technical-term policy for `th.json`: keep vendor/protocol terms in their original English spelling, translate the surrounding explanation.** Users configuring Modbus hardware in Thailand are already working from English vendor manuals and English gateway config pages (e.g. Elfin EW11's own web UI), so translating terms like `Modbus`, `AB Bus`, `unit-id`, `RS-485`, `TCP`, `DIP switch`, `SW1`/`SW2`, `gateway`, `register`, `baud rate`, `entity ID`, `TA`/`TCJ`/`TC2`/`TE`/`TO`/`TD`/`TS`, `AB64`, or `Home Assistant` itself would create a mismatch with what the user sees everywhere else, not an improvement. This applies to the `entity` block too — parenthetical register abbreviations like `(TA)`, `(TCJ)`, `(TC2)`, `(TE)`, `(TO)`, `(TD)`, `(TS)` stay exactly as-is in the Thai sensor names. Example: "ที่อยู่ของกล่อง AB64 บน gateway — unit-id = SW2 × 16 + SW1 + 1", not a fully-Thai paraphrase of "unit-id" or "gateway".
  - **`compressor_current` and `compressor_rpm` translations must not imply a unit the English original doesn't state.** Per the advanced-telemetry decision above, compressor current has no confirmed unit and compressor speed is `rps` not `rpm` — the Thai `entity.sensor` names for these two must stay as unit-free as their English counterparts (no "(A)", no "(รอบ/นาที)" or similar invented in translation).
  - **Permanent maintenance burden, not a one-time task: any future edit to `strings.json` (any of its three blocks) must be mirrored in `th.json`.** A key present in `strings.json` but missing (or misspelled) in `th.json` does **not** error — it silently falls back to English for that one string, which is easy to miss in review. A key-parity test (see `qa-engineer.md`/`plan-thai.md`) catches missing/extra *keys*, but nothing automated catches Thai *content* going stale when the English wording changes — that still needs a human to notice during review.
- **Decision 2026-08-07 — reverses the "unit unknown" call on `filter_sign_timer` (register 4020): confirmed to be hours the unit has been running.** Previously this field carried no `device_class`/unit, the same "insufficient evidence" treatment given to `compressor_current` above — see the "Filter-sign timer unit: Unknown" row in `README.md`'s confirmation-status table, now updated to reflect this. Two independent tick measurements confirmed a 1-hour period on 2026-08-07: `4272→4273` during `15:05:34`–`15:07:34`, and `4273→4274` during `16:05:56`–`16:07:56`, ~60 minutes apart both times. The AC was in `cool` mode for the full two hours measured, so the tick counts hours **the unit is running**, not wall-clock hours. Separately, the raw value itself (4272) is consistent with the unit's install date (~570 days earlier) at ~7.5 hours/day of runtime — a figure the owner gave independently, before being told this number, as "the office runs it about 8 hours a day." A 24/7-runtime assumption is ruled out by the same math (~13,700 expected, not 4,272 observed). Full evidence table: `.claude/shared/plan-cleanup.md`, "รอบ 2" section.
  - **Why this field gets a unit while `compressor_current` still doesn't (see above)**: `compressor_current` has only one line of evidence (the observed raw range), which forces guessing a scaling factor — an unfalsifiable guess with data from a single unit. This field has **two independent lines of evidence** (a directly-measured tick period, and a value magnitude that matches an independently-known usage figure) and needs **no multiplier or divisor at all** — 1 raw unit = 1 hour, exactly. The evidence bar for adding a unit hasn't moved; this field just happens to clear it where `compressor_current` doesn't.
  - Values applied: `device_class: duration`, `unit_of_measurement: UnitOfTime.HOURS`, `state_class: total_increasing` (an increasing counter that can drop on a filter reset — HA treats a drop under `total_increasing` as a legitimate reset, not a bad reading).
  - **`enabled_default` stays `False`** — this doesn't change the opt-in/default-on line drawn in the advanced-telemetry decision above. That bar is "confirmed present on every model this integration has seen" (currently just TA); confirming the *unit* of an already-opt-in field doesn't promote it to default-on. It's still one of the 11 advanced sensors gated behind "Enable advanced telemetry sensors."
